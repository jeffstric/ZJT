1. **升级后第一次打开页面会被要求重新登录**——登录体系切换的正常表现，重新登录一次即可。
2. 登录成功后，浏览器会**同时**在 Cookie 和 localStorage 保存凭证（兼容期双写，属预期）。
3. 上传图片/视频有了**大小限制**：图片 10MB、视频 200MB、音频 50MB，超限会明确报错。

## 三、主题① 登录认证改造（重点，约 40 分钟）

### 背景
以前登录凭证（token）放在浏览器 localStorage，脚本窃取风险高；现在挪进 HttpOnly Cookie（JS 读不到，更安全）。改造覆盖 26 处入口和 7 处后端消费点，兼容期**双写**过渡。

### A 组：登录态一致性

| 编号 | 步骤 | 预期结果 |
|------|------|----------|
| A1 | 登录后开第二个标签页打开首页 | 第二个标签页直接是登录态，不需要再登录 |
| A2 | 登录后手动清掉 Local Storage 里的 `auth_token` 和 `logged_in`（保留 Cookie），刷新页面 | 弹出登录框并提示"登录方式已更新，请重新登录"（**设计行为**：兼容期 cookie 不能当作完整登录态，强制重新登录以免空 token 进页面）。**不允许**出现"看起来登录了但接口全 401"的中间态 |
| A3 | 登录后（本地有 token）在地址栏访问 `http://localhost:16000/?login=1` | **不弹**登录框（会话有效时 `?login=1` 不误弹，且按 redirect_url 跳转） |
| A4 | 同一账号重新登录（另一个浏览器/接口登录） | 互踢为**全局单 token 生效**：旧会话 token 立即失效（接口 401）；旧页面操作后自动跳转 `/?login=1&redirect_url=当前页`，重新登录后**跳回原页面**（不再硬编码跳视频工作流列表） |
| A5 | 登录 → 登出 → 再登录，重复 3 次 | 每次登录/登出行为一致，无残留旧 token 导致 401 |

### B 组：登录态覆盖各功能入口（逐个点一遍）

| 编号 | 入口 | 预期 |
|------|------|------|
| B1 | 首页"剧本创作"卡片 | 已登录时直接进入，不误判未登录 |
| B2 | 首页"故事板"卡片 | 同上 |
| B3 | 故事板列表页（storyboard_list） | 列表正常加载，不误报登录过期 |
| B4 | 视频工作流列表页 → 打开一个工作流 | 算力数字正常显示；任务轮询正常 |
| B5 | 画布里的世界/角色/场景/道具选择器 | 能正常弹出并加载数据 |
| B6 | 管理后台 → 许可证页面 | 正常加载 |
| B7 | 算力日志弹窗（视频工作流页） | 正常打开并显示记录 |

### C 组：走 token 的后端链路（cookie 会话用户最容易断的地方）

| 编号 | 步骤 | 预期 |
|------|------|------|

### E 组：XSS 注入防护

> XSS = 把代码当内容塞进页面执行。验证方法：让 AI 输出或把下面文本填进能渲染富文本的地方。

## 八、配套自动化测试现状与补充建议

已随本次改动合入的自动化（可作为手工回归的"保险网"）：

| 层级 | 已有 |
|------|------|
| 后端单元/接口 | `tests/api/test_require_permission_auth.py`（鉴权装饰器）、`tests/utils/test_media_upload.py`（上传收口）、`tests/utils/test_world_docx.py`（Word 导出+路径穿越）、`tests/llm/test_shot_pack.py`、`tests/script_writer_core/test_ensure_narrator_character.py`（旁白角色）、`tests/services/test_storyboard_character_bootstrap_service.py`、`tests/llm/test_script_split_total_duration.py`（时长控制） |
| 前端（node 断言） | `web/tests/security.test.js`（XSS 净化）、`web/tests/canvas_groups_clipboard.test.js`（分组/复制粘贴）、`web/tests/index_login_token_verify.test.js`（登录判据）、`web/tests/storyboard_reference_to_video.test.js`、`web/tests/shot_node_theme.test.js`（暗色）等 11 个 |
| CI 静态拦截 | `scripts/lint_frontend_xss.py`（X1~X4）、签名一致性/迁移命名/阻塞调用等既有 lint |

**建议补充（按性价比排序）：**

1. **e2e（最有必要）——登录态全链路**：Cookie 双通道改造涉及 26 处入口，单元测试只覆盖了判据函数，"登录→刷新→登出→顶号→probe 自愈"这条链只有 e2e 能兜住。建议用 Playwright 写 1 条核心链路（登录→访问 5 个主页面→登出→刷新），这是本次风险最高、自动化收益最大的点。
2. **e2e——保存冲突（K1/K2）**：409/滚动 CAS 基线逻辑横跨前端 lastSeen 与后端内容哈希，单测各自为政，双标签页竞争场景适合一条 e2e 覆盖。
3. **前端测试——分组持久化**：`canvas_groups_clipboard.test.js` 测了操作逻辑，但"刷新后分组复原"（I6）依赖保存/加载序列化链路，建议补一条针对分组 JSON 持久化 round-trip 的断言。
4. **后端单测——滑动续期并发**：`get_user_id_by_token` 收口续期后，同 token 并发请求的续期幂等性值得加一个并发用例（多线程同 token 调用不产生重复行/异常）。
5. **CI 校验——模型/迁移完备性**（本轮缺陷①的教训）：可加一个轻量 CI 检查——对 `model/*.py` 的 `CREATE_TABLE_SQL` 与最新迁移链做字段比对（或启动时对存量表做"列缺失自动补齐+告警"），防止"改了建表 SQL 但漏写存量迁移"再次发生。
