# 剧本节点自动拆分分镜功能改进

## 更新日期
- 2026年2月3日：自动生成分镜功能
- 2026年2月4日：新增"旁白视为对话"功能
- 2026年2月7日：将"旁白视为对话"升级为"解说剧（仅旁白说话）"，新增对话剧本→纯旁白剧本的LLM转换步骤
- 2026年5月16日：修复自动生成分镜节点时视频模型偶发回退默认值的问题
- 2026年7月1日：分镜组拆分改为优先按 story-writer 场景/幕边界分组，不再贪婪填满最大分镜组时长
- 2026年7月1日：剧本到分镜提示词补充分镜设计规则，包括叙事目的、摄影角度、动作-反应结构和镜头技巧

## 功能概述

优化了剧本节点的"拆分镜组"功能，使其更加智能和便捷。现在点击"拆分镜组"按钮后，系统会自动完成以下操作：

1. **检查重复拆分**：检测剧本节点下是否已有分镜组节点，避免重复拆分
2. **自动生成分镜**：为每个分镜组自动调用"生成分镜"功能，无需手动点击
3. **场景/幕优先分组**：优先参考 story-writer 标准场景标记和幕/场结构，不为了凑满最大时长跨场景合并
4. **分镜设计规则**：每个镜头补充摄影角度、叙事目的和可见动作要求，提升镜头存在理由的明确度
5. **视频模型继承**：自动生成的分镜节点继承分镜组或接口返回的视频模型配置

## 功能改进详情

### 1. 重复拆分检测

**改进前**：
- 用户可以多次点击"拆分镜组"按钮
- 每次点击都会创建新的分镜组节点
- 导致重复的分镜组和混乱的工作流

**改进后**：
- 点击"拆分镜组"前，系统会检查是否已存在分镜组节点
- 如果已有分镜组，显示提示："已有分镜组，请勿重复点击"
- 防止用户误操作导致的重复拆分

**实现逻辑**：
```javascript
// 检查是否已有分镜组节点
const existingShotGroups = state.connections.filter(c => c.from === id);
if(existingShotGroups.length > 0) {
  const hasShotGroupNode = existingShotGroups.some(conn => {
    const targetNode = state.nodes.find(n => n.id === conn.to);
    return targetNode && targetNode.type === 'shot_group';
  });
  
  if(hasShotGroupNode) {
    showToast('已有分镜组，请勿重复点击', 'warning');
    return;
  }
}
```

### 2. 自动生成分镜

**改进前**：
- 拆分镜组后，需要手动点击每个分镜组的"生成分镜"按钮
- 对于包含多个分镜组的剧本，操作繁琐

**改进后**：
- 拆分镜组后，自动为每个分镜组生成分镜节点
- 状态提示实时更新，显示生成进度
- 完成后显示总结信息

**实现逻辑**：
```javascript
// 创建分镜组节点数组
const createdShotGroupNodes = [];
result.data.shot_groups.forEach((shotGroup, index) => {
  const shotGroupNodeId = createShotGroupNode({...});
  if(shotGroupNodeId) {
    createdShotGroupNodes.push(shotGroupNodeId);
  }
});

// 自动为每个分镜组生成分镜
statusEl.textContent = '正在自动生成分镜...';
for(const shotGroupNodeId of createdShotGroupNodes) {
  const shotGroupNode = state.nodes.find(n => n.id === shotGroupNodeId);
  if(shotGroupNode) {
    await generateShotFramesIndependentAsync(shotGroupNodeId, shotGroupNode);
  }
}
statusEl.textContent = `已完成：${createdShotGroupNodes.length}个分镜组，所有分镜已自动生成`;
```

### 3. 视频模型继承与字段兼容

**问题场景**：
- 拆分镜组接口返回的视频模型字段可能使用 `video_model` 等命名
- 前端节点历史字段使用 `videoModel`
- 如果字段未兼容，分镜组或自动生成的分镜节点会落回默认视频模型
- 如果任务配置尚未加载完成，默认值可能使用硬编码回退值

**改进后**：
- 创建分镜组时兼容读取 `videoModel`、`video_model` 等字段
- 自动创建分镜节点时透传分镜组的 `videoModel`
- 创建节点前优先等待 `TaskConfig` 加载完成，降低默认模型竞态
- 仅在接口和父节点均未提供视频模型时才使用默认值

### 4. 分镜组按场景/幕边界拆分

**改进前**：
- `llm/script_parser.py` 会把 LLM 返回的所有镜头拉平，再按 `max_group_duration` 贪婪合并
- 两个不同 story-writer 场景即使各自语义独立，只要总时长未超限，也可能被合并为一个分镜组
- 某个场景被拆分后，下一场景的镜头可能被拉入上一组以补足时长

**改进后**：
- LLM 提示词明确要求优先按 story-writer 标准场景标记分组，例如 `[场景 地点 时间段]`、`场景编号：A1`
- 没有标准场景标记时，按 `第一幕`、`第二幕`、`第X场` 等幕/场结构作为兜底边界
- 后处理 `reorganize_shot_groups` 保留原语义分组，不再跨场景、跨幕、跨场贪婪合并
- `max_group_duration` 只作为安全上限：当同一个场景或同一幕内部总时长超限时，仅在该语义分组内部拆分

**示例**：
```text
A1 场景：镜头1 6秒
B1 场景：镜头2 6秒
max_group_duration = 15秒
```

即使两个镜头合计 12 秒，也会保留为两个分镜组，因为它们属于不同 story-writer 场景。

### 5. 剧本到分镜提示词增强

`llm/script_parser.py` 的提示词保留了与现有结构兼容的分镜方法：

- 九列分镜表被映射到现有 JSON 字段：镜号、时长、摄影角度、景别、画面内容、场景、声音、备注和叙事目的。
- shot 新增 `camera_angle` 与 `narrative_purpose` 字段，shot_group 新增 `group_type` 字段；旧字段保持不变，后续流程仍可读取原来的 `shot_type`、`camera_movement`、`description`、`scene_detail` 等字段。
- `narrative_purpose` 必须从建立、推进、揭示、强调、过渡、情绪、反射七类中选择，并说明具体视听手段，避免只写“推进剧情”。
- 画面内容要求使用可见动作句，不写心理活动；关键道具必须点名，且继续遵守道具名称不能写成 `prop_001` 的规则。
- 镜头设计可参考动作-反应结构、构图、运动、衔接、转场和主观镜头技巧，但不得为了炫技牺牲清晰叙事。

与现有逻辑可能冲突的内容已降级为软目标：

- “Clip 4~15 秒”在系统中表现为尽量让分镜组达到 4 秒以上，但 `max_group_duration` 仍是硬上限。
- “短镜必须合并”改为“短镜优先并入同一场景或同一幕内的相邻镜头”，不得跨场景、跨幕强行合并。

### 6. 新增异步生成函数

为了支持自动批量生成分镜，新增了 `generateShotFramesIndependentAsync` 函数：

**特点**：
- 异步执行，支持在循环中使用 `await`
- 与原有的 `generateShotFramesIndependent` 函数逻辑相同
- 不显示 Toast 提示，避免批量生成时的提示信息过多
- 返回创建的分镜节点数量

**函数签名**：
```javascript
async function generateShotFramesIndependentAsync(shotGroupNodeId, shotGroupNode)
```

## 注意事项

1. **检测范围**：只检测直接连接到剧本节点的分镜组，不检测间接连接
2. **异步执行**：自动生成分镜是异步执行的，按顺序依次生成每个分镜组
3. **错误处理**：如果某个分镜组生成失败，不会影响其他分镜组的生成
4. **性能考虑**：对于包含大量分镜的剧本，自动生成可能需要较长时间

## 兼容性

- 与现有的手动"生成分镜"功能完全兼容
- 不影响已有的工作流数据
- 支持工作流的保存和加载

## 未来优化方向

3. **取消功能**：支持取消正在进行的自动生成

## 当前状态：解说剧拆分模式已移除

`解说剧（仅旁白说话）` 已从剧本拆分链路移除。前端不再显示该选项，后端也不再支持 `narration_as_dialogue` 特殊解析参数、对话剧本转纯旁白剧本的转换函数和兜底旁白后处理。旁白解说能力改由世界级 `story_type=narration` 和脚本智能体流程管理。
