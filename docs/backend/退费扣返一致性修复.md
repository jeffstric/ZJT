# 退费扣返一致性修复（多供应商切换退费事故）

> 事故日期：2026-08-19　|　涉及用户：15155011268（user_id=1534）等 5 人　|　状态：已修复

## 1. 事故现象

用户反馈 Grok 生视频「每次扣 16 分，生成失败返还 80 分」。经查 `computing_power_log`，用户反复触发失败任务，每次净赚 64 分，累计刷取约 1.9 万算力（管理员已手动抹除并留存奖励）。

## 2. 根因

Grok 图生视频（type=27）多供应商价格不同（15 秒档）：

| 实现方 | 6s / 10s / 15s |
|---|---|
| `grok_duomi_v1`（多米） | 8 / 8 / **16** |
| `grok_common_site0_v1`（ZJTapi） | 35 / 55 / **80** |
| `grok_common_site1~5` | 6 / 8 / 12 |

故障链条：

1. **扣费**：任务创建（`server.py`）按当时选中的实现方 duomi 扣 16 分，扣费流水号写入 `ai_tools.transaction_id`；
2. **供应商切换**：duomi 提交失败 → 企业版 before_finish 重试 → `ImplementationRetryPipelineDriver.execute()`（`task/pipeline_drivers/implementation_retry_driver.py`）**把 `ai_tools.implementation` 改写为切换后的实现方**（site0=42）；
3. **退费**：备用供应商也失败 → 旧退费逻辑读取 `ai_tool.implementation`（已被改写）**按当前配置重新计算**退费金额 → 15 秒 = 80 分 → 多退 64 分。

**共性设计缺陷**：退费金额靠「重算」而非「按实际扣减流水原额退还」。因此除了供应商切换，价格热更新（`implementation_power_config` 改价）同样会造成扣返不一致。

## 3. 修复方案

**核心：退费金额以实际扣减流水为准。** `ai_tools.transaction_id` 与 `computing_power_log.transaction_id` 1:1 绑定（任务创建时同时写入），是精确对账依据。

### 3.1 三级回退（`utils/computing_power.py: resolve_refund_amount`）

1. **扣费流水**：按 `ai_tools.transaction_id` 查 `computing_power_log` 实际扣减金额，原额退还（精确，免疫供应商切换/价格热更新）；
2. **重算**：`get_computing_power_for_task()` 按当前配置重算（流水缺失时兼容回退）；
3. **静态配置**：`TASK_COMPUTING_POWER[type]` 兜底（最旧数据）。

### 3.2 幂等防重复退费

- 退费流水号从随机 uuid 改为 **`refund-{原扣费流水号}`**，与任务 1:1 对应；
- 退费前 `is_already_refunded()` 检查该流水是否已存在（依赖 perseids 服务将退费流水写入同一 `computing_power_log` 表；check-then-post 存在极小竞态窗口，仅作防御加固）。

### 3.3 查询索引

`computing_power_log.transaction_id` 原无索引（按流水号查询全表扫描），新增单列索引 `idx_transaction_id`：

- 迁移脚本：`alembic/versions/20260819_power_log_txn_idx.py`（revision `20260819_txn_idx`）
- `model/computing_power_log.py` 末尾 `CREATE_TABLE_SQL` 已同步

## 5. `transaction_id` 不可变性验证（修复方案前提）

修复依赖「`ai_tools.transaction_id` 自任务创建后不被改写」。已从三方面验证：

1. **代码写入点**：全库（含企业包）所有 `transaction_id` 写入均为任务创建时的
   `AIToolsModel.create` / `create_with_pipeline_steps` / `AIAudioModel.create`（扣费同时写入），
   任务生命周期内无任何 `update` 调用传入 `transaction_id`；
2. **供应商切换链路**：企业版 `enterprise/task/retry_handler.py` 的 `AIToolsModel.update`
   只更新 `status`/`message`；开源 `ImplementationRetryPipelineDriver` 只更新
   `implementation`/`status`/`project_id`/`message`——只有 `implementation` 被改写（即事故根因），
   `transaction_id` 不动。设计上也自洽：切换重试**不重新扣费**，扣费凭证无需变更；
3. **线上数据实证**（2026-08-19 全天 297 个发生切换的 Grok 失败任务）：扣费日志时间与任务
   创建时间滞后全部为 0 秒、金额全部为首次实现方价格（16×294 + 8×3）、任务与扣费流水
   100% 一对一关联——若流水号在切换中被改写，上述三项必然出现偏移。

⚠️ **维护约束**：`AIToolsModel.update` / `update_by_project_id` 的字段白名单仍包含
`transaction_id`（机制上可写）。后续新增代码**禁止**在任务创建后更新该字段；即使误更新，
退费侧的三级回退（查不到流水 → 重算）也不会比旧逻辑更差。另：`computing_power_log` 中
`token_log_` 前缀的流水（LLM token 扣费）存在同号多条的情况，与 `ai_tools` 无关，
按流水查询时已带 `user_id` 过滤 + `ORDER BY id DESC LIMIT 1`，不受影响。

## 6. 历史数据审计

修复前退费流水与扣费流水无关联，无法直接 SQL 对账。可按事故模式粗筛（同时段同用户「16 扣 + 80 返」）：全局多退约 2.6 万分。修复后新产生的退费流水带 `refund-` 前缀，可精确对账：

```sql
-- 扣返不一致审计（新数据）
SELECT a.id, a.user_id, d.computing_power AS deducted, r.computing_power AS refunded
FROM ai_tools a
JOIN computing_power_log d ON d.transaction_id = a.transaction_id AND d.behavior = 'deduct'
JOIN computing_power_log r ON r.transaction_id = CONCAT('refund-', a.transaction_id)
WHERE d.computing_power != r.computing_power;
```
