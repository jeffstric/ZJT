## 0. 背景速览（测试前必读）

**事故**：Grok 图生视频任务按 `grok_duomi_v1`（15秒=16分）扣费后，若该供应商提交失败，系统自动切换到备用供应商 `grok_common_site0_v1`（15秒=80分）重试，**切换过程会改写 `ai_tools.implementation` 字段**。旧退费逻辑按这个被改写后的实现方价格重算退费金额，导致「扣16分、失败返还80分」，用户每次失败任务净赚64分。

**修复机制**（被测对象）：

1. **退费金额三级回退**（`utils/computing_power.py: resolve_refund_amount`）：
   - 第一优先：按 `ai_tools.transaction_id` 查 `computing_power_log` 扣费流水，**原额退还**；
   - 回退1：按当前配置重算（`get_computing_power_for_task`）；
   - 回退2：静态配置 `TASK_COMPUTING_POWER`。
2. **退费幂等**：退费流水号 = `refund-{原扣费流水号}`，退费前检查已存在则跳过（`is_already_refunded`）。
3. **索引**：`computing_power_log` 新增 `idx_transaction_id(transaction_id)`。

**修复覆盖的退费代码路径**（全部在 `task/visual_task.py`）：
`_refund_computing_power`、`_handle_task_failure` 退费块、超最大重试退费块。
（`task/sync_task_executor.py` 委托上述函数；`video_task.py` 为无引用的废弃文件，不在版本库。）

### C2. 修复部署后的线上验证（部署后执行，只读）

> ⚠️ 此用例只能在修复代码部署到生产之后执行。判定依据：部署时间点之后新产生的失败任务。

```sql
-- 新失败任务的退费流水应带 refund- 前缀，且金额=原扣减金额
SELECT a.id AS task_id, a.user_id, a.create_time,
       d.computing_power AS deducted, r.computing_power AS refunded
FROM ai_tools a
JOIN computing_power_log d ON d.transaction_id = a.transaction_id AND d.behavior='deduct'
LEFT JOIN computing_power_log r ON r.transaction_id = CONCAT('refund-', a.transaction_id) AND r.behavior='increase'
WHERE a.status = -1 AND a.create_time >= '<部署时间>'
ORDER BY a.id DESC LIMIT 20;
```

**判定**：
- `refunded` 列与 `deducted` 列**逐行相等** → ✅ 修复生效；
- `refunded` 为 NULL 但任务已失败超过重试周期（约10分钟） → ⚠️ 退费未发起，需查服务日志 `Refunding` / `already refunded`；
- 部署后新退费流水中**不应再出现**与扣减金额不一致的记录：

```sql
-- 扣返不一致审计（部署后新增数据应为 0 行）
SELECT a.id, d.computing_power, r.computing_power
FROM ai_tools a
JOIN computing_power_log d ON d.transaction_id = a.transaction_id AND d.behavior='deduct'
JOIN computing_power_log r ON r.transaction_id = CONCAT('refund-', a.transaction_id)
WHERE a.create_time >= '<部署时间>' AND d.computing_power != r.computing_power;
```

## 3. 边界与已知无关现象（防误判）

| 现象 | 结论 | 说明 |
|---|---|---|
| `computing_power_log` 中 `token_log_` 前缀流水同号多条 | ✅ 无关 | LLM token 扣费（`task/token_task.py`），不关联 `ai_tools`；查询带 `user_id` 过滤 + `LIMIT 1` 不受影响 |
| 老任务（修复前创建）失败重试后按重算金额退费 | ✅ 预期内 | 仅流水查不到时走回退；新任务不受影响 |
| `ai_tools.transaction_id` 为空的历史任务 | ✅ 预期内 | 走回退重算，与旧逻辑一致，不会更差 |
| 退费流水号仍为随机 uuid（不带 refund- 前缀） | ❌ 异常 | 说明走的旧代码路径或回退分支，需核查部署版本 |
| 成功任务也出现退费流水 | ❌ 异常 | 退费只在失败/超最大重试路径触发，需上报 |
